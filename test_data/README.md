# Evaluation Dataset — Retail Intelligence System

## Purpose

This dataset is supplementary evidence for Chapter 4 of the dissertation
"AI-Powered Retail Intelligence System for SME Retailers in Sierra Leone."
It is a synthetic/test data export from the project's development database,
provided so the sales, inventory, customer, and forecasting data referenced
in the evaluation chapter can be inspected directly rather than taken on
faith.

This is synthetic and demonstration data. It is not a record of real
retail transactions, and it does not represent real customers. It was
generated by two Django management commands already present in the
project's source tree (seed_retail_data.py and
seed_demo_customer_history.py), which construct plausible transaction
histories, customer behaviour archetypes, and browsing activity against
the project's real product catalogue, for the purpose of exercising and
testing the system's AI-driven features during development.

## What this dataset is NOT

- It does not represent the real Sierra Leonean retail market.
- It is not statistically representative of any real customer population.
- It does not prove real-world effectiveness of the system's AI features;
  it demonstrates that those features run correctly against realistic,
  structured input data.
- It does not include Cost of Goods Sold (COGS) data; no COGS field
  exists in this project's schema, and COGS is explicitly outside the
  scope of the dissertation.

## Dataset boundary and how synthetic records were identified

Records were included only where they carry an explicit, code-verified
synthetic marker already used elsewhere in the project, not a marker
invented for this export.

Sources and identifying markers:
- seed_retail_data.py customers: email ends @seed.retailintel.local
- seed_demo_customer_history.py customers: email ends @demo.retailintelligence.local
- Walk-in sales (no customer): Sale.notes contains [SEED] walk-in sale
- Online-order-linked sales: linked via an included synthetic customer's order
- Stock receipts: notes contains [SEED]
- Inventory adjustments: reason contains [SEED]
- Expenses: description contains [SEED]

Two manually-created customer accounts, using real personally-owned email
addresses created directly by the dissertation author during development
rather than by either seed command, were identified during inspection and
deliberately excluded from every file in this dataset.

File: inventory_adjustments.csv — 102 rows — model inventory.InventoryAdjustment
File: expenses.csv — 240 rows — model expenses.Expense
File: demand_forecasts.csv — 122 rows — model forecasting.DemandForecast (latest per product)
File: customer_insights.csv — 170 rows — model customer_insights.CustomerInsightSnapshot (latest per customer)
File: customer_events.csv — 1504 rows — model customer_insights.CustomerEvent

Date range: transaction data spans approximately September 2025 to
August 2026 (about 12 months), matching the default window of
seed_retail_data.py. Exact per-file ranges, verified from the exported
data rather than assumed:
- sales.csv: 2025-09-03 to 2026-08-26
- online_orders.csv: 2025-09-19 to 2026-08-26
- expenses.csv: 2025-09-01 to 2026-08-24

Products (evaluation product catalogue): all 122 Product rows
currently in the database are exported in full. This is the real,
current product catalogue used across the system, not itself
seed-generated. seed_retail_data.py builds transaction history on top
of this existing catalogue rather than creating it. No origin claim
beyond this is made; the catalogue's provenance prior to this export is
outside what could be verified from the code inspected for this export.

Customer intelligence and forecasting: demand_forecasts.csv and
customer_insights.csv are append-only tables in the live system;
every time forecasts or insights are regenerated, new rows are added
without deleting old ones. Neither model carries a synthetic-data marker.
To avoid presenting repeated test-run history as a curated longitudinal
record, only the latest row per product (forecasts) or per
customer (insights) is exported here, matching how the live system
itself consumes these tables (the AI Business Advisor always reads the
latest forecast per product). The live development database contains
more forecast-generation history than is reflected in this snapshot.

## Limitations of synthetic test data

- Behavioural patterns (order frequency, basket composition, customer
  archetypes) were generated by weighted-random logic designed to be
  plausible, not measured from real shoppers.
- Product popularity tiers, seasonal effects, and customer archetypes
  were parameterised by the dissertation author, not derived from
  observed retail data.
- Findings drawn from this dataset demonstrate that implemented features
  execute correctly against structured, realistic-shaped data. They are
  not evidence of real-world accuracy or effectiveness, and Chapter 4/5
  do not claim otherwise.

## Relationship to the dissertation

This dataset is supplementary evidence only. The dissertation document
itself remains the primary source for findings, interpretation, and
discussion of results. Nothing in this dataset's presence resolves or is
intended to resolve any of the documentation discrepancies already
disclosed in Chapters 4 and 5 of the dissertation; those disclosures
stand independently of this export.

## Reproducibility

Generated via a dedicated, read-only Django management command:

python manage.py export_evaluation_data

located at products/management/commands/export_evaluation_data.py in
this repository. The command never calls .save(), .create(),
.update(), or .delete() on any model; it reads exclusively via
.values() querysets, so it cannot modify the underlying database.
Running it against the same development database will reproduce this
same dataset, subject to any changes made to that database since this
export was generated.

Version/date of this export: generated August 2026, from the project
database as it existed at that time.

## What was excluded, and why

The following fields and tables were deliberately excluded from every
file:

- OnlineCustomer.password (hashed customer credentials)
- Sale.served_by, Expense.recorded_by, StockReceipt.received_by,
  InventoryAdjustment.adjusted_by: all foreign keys to real staff
  accounts, dropped as columns entirely rather than masked, since staff
  identity was not necessary for any of the evaluation purposes this
  dataset supports.

No passwords, password hashes, API keys, tokens, SECRET_KEY, .env
values, or other credentials appear anywhere in this dataset, verified
via a full-file grep sweep prior to publication.
